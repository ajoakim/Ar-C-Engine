  <name>Task 1: Integer counts, decimal times (DEBT-04) and scale factor in debug-ui (DEBT-02)</name>
  <files>crates/debug-ui/src/lib.rs</files>
  <behavior>
    - fmt_count(593.0) == "593"; fmt_count(0.0) == "0"; fmt_count(2.5) == "2.50"; fmt_count(-3.0) == "-3"; fmt_count(NAN) == "n/a"; fmt_count(1e20) does not print a 21-digit integer via a lossy cast (falls back to decimals or scientific, no panic)
    - fmt_ms(8.3) == "8.30"; fmt_ms(8.0) == "8.00"; fmt_ms(NAN) == "n/a"
    - panel text for a snapshot with gauge("selected", 593.0) contains "selected: 593" and not "593.00"; frame/prepare line keeps "8.30"
    - frame_shapes with scale 2.0 and size [1600, 1200] pixels yields pixels_per_point == 2.0 and shapes laid out for an 800x600-point screen (the window anchors at (8,8) points = 16 pixels); scale 1.0 yields the same primitives as before the change
    - non-finite or non-positive scale falls back to 1.0
  </behavior>
  <action>
1. Replace `fmt_value` by two functions: `fmt_count(v)` (finite and `v.fract() == 0.0` and `v.abs() < 1e15` => `format!("{}", v as i64)`; other finite => `{v:.2}`; non-finite => "n/a") used for gauges and both numbers of a budget text, and `fmt_ms(v)` (`{v:.2}` or "n/a") used for frame_ms and prepare_ms. No label-based special casing: a genuinely fractional gauge (a ratio) still gets decimals through fmt_count; a whole-valued ratio of exactly 1.0 printing as "1" is accepted and documented in the doc comment (the only fractional-by-nature values in the snapshot, frame/prepare ms, have the dedicated function).
2. Add scale support: `frame_shapes(ctx, size, scale_factor: f32, time, snapshot)` (new parameter after `size`, update `frame_shapes_observed`, all tests in this file, and note the engine-sdk caller is changed in task 3). Sanitise `scale = if finite and > 0 { scale } else { 1.0 }` clamped to at most 8.0. Call `ctx.set_pixels_per_point(scale)` before the passes and set `screen_rect` to `size / scale` points (after the existing size sanitisation, keep the min 1.0 point rule). Tessellate with the egui-reported `output.pixels_per_point`. Doc comment: `size` is in physical pixels.
3. Tests per <behavior>. For the scale test run `frame_shapes` twice (scale 1.0 and 2.0, fresh Context each) and assert ppp values and that the 2.0 mesh's first vertex x is about twice the 1.0 one (anchor offset 8 points -> 8 vs 16 pixels); use a tolerance, do not compare whole meshes. Keep the three existing tests (adjusting the call signature only; do not loosen them).
  </action>

  </verify>
