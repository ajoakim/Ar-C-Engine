## Root cause

1. Stutter cause: selection blow-up past the tau-escalation cap. CONFIRMED (`base-release-bench.csv`, `base-debug-bench.csv`, `base-release-window.csv`). Once the camera is below ~4 km, `select` cannot bring the leaf count under `max_leaves = 700` even at tau_steps = 8 (tau_eff 51.26 px, the cap `max_tau_steps = 8`); wanted_leaves jumps from ~660 to 5115 in one frame and saturates near 164k, nodes_visited ~2.0M per frame. prepare_ms (selection incl. up to 9 reruns) is 99%+ of the frame: release 660-1000 ms/frame (~1.4 fps), debug ~10 s/frame; gpu_frame stays 0.4-6 ms (release). So the stutter is CPU selection cost, not GPU or drawing. The exact mechanism of the 164k plateau (2:1 balance forced splits and/or min_distance/max_level 19 interplay with a capped tau) is SUSPECTED, not isolated: forced_splits is not in the CSV; plan 07.1-02 should log it.
2. Tau-escalation reruns x8: CONFIRMED as a multiplier. tau_steps = 8 on every frame below ~4.1 km, each rerun repeating the whole traversal (nodes_visited counts the final pass only; cost is up to 9x of that). Contribution to per-frame cost: SUSPECTED large, not separately timed.
3. Unbounded leaf counts: CONFIRMED. max_leaves is only a soft target (selection returns the over-limit result when the tau cap is reached); wanted_leaves reached 164,181 vs limit 700 (`base-release-bench.csv`).
4. Silent draw drops past MAX_DRAWS_PER_FRAME: REFUTED in these runs (draw_overflow max 0, drawn_leaves max 615; `base-release-window.csv`). Code path exists (`system.rs` draw loop increments `overflow` and skips) but was never triggered, because drawn leaves are limited by held meshes, not wanted leaves.
5. Streaming starvation: CONFIRMED as a symptom. With wanted ~164k, pending/in_flight/awaiting_upload rise (release window max pending 248, in_flight 769, awaiting_upload 765), uploads <= 4 per frame and started <= 8 per frame; at ~1.4 fps the terrain refines glacially. held_meshes keeps creeping up while hovering (1186 -> 1534 over 1140 frames; max 1744): bounded-ness of held growth is SUSPECTED unbounded (not shown to plateau within 1440 frames).
6. Crash: NOT REPRODUCED in any of the four runs (no panic, no abort, no event-log entry; `target/diag/*.err`, `eventlog.txt`). Run lengths: debug bench 300 frames then timeout; debug window 180 frames then timeout; release bench 600 frames complete; release window 1440 frames then timeout (900 s). Suspects:
   - near-full disk / pagefile: REFUTED for this machine today (190G free, pagefile usage 141/8192 MB, peak working set 204 MB). Cannot speak to the earlier crash conditions (disk was reported full then); SUSPECTED as the original trigger but not reproducible now.
   - wgpu uncaptured-error panic: SUSPECTED as a latent crash path (no handler installed, CONFIRMED by grep), but no error was observed (stderr clean).
   - device lost: REFUTED in these runs (no device-lost text), no handler exists to report one either.
   - stack overflow / access violation / fail-fast: REFUTED in these runs (no event log entries, no stderr text; debug window ran ~15 min at 10 s/frame without crashing).
   - memory growth to OOM: REFUTED in these runs (peak 204 MB).
   An unattended crash may also come from the user killing/closing a window that appears frozen at ~0.1-1.4 fps; this is SUSPECTED and unverified.

## Flicker (plan 07.1-20)

User report (a): on the hex default, release, `--descent --fast`, "flickering of green patches".

### Decision table (stated BEFORE any measurement)

Counters (opt-in, `TerrainConfig.diagnostics`): `level_changes`, `drawn_appeared`, `drawn_disappeared`, `cull_toggles`, `overlap_pairs`, `flipflops`, `flipflops_unexplained`. Absolute invariants: `overlap_pairs == 0` always; with the camera frozen after convergence `level_changes == drawn_appeared == drawn_disappeared == cull_toggles == 0`; in a monotone descent `flipflops_unexplained == 0`. Non-zero is evidence for a cause, never a limit.

| Row | Rule (hit when) |
|---|---|
| A1 selection churn | `flipflops_unexplained > 0` on the monotone fast descent: the 0.2 hysteresis is bypassed (candidates: `prev_split` dropped for cells culled in the previous frame; trim order under the leaf budget) |
| A2 residency churn | cells drawn in the last 8 frames are destroyed by the LRU (`destroyed > 0`) and later re-requested: appear/disappear with no select-level change |
| B cull toggling | `cull_toggles > 0` while `level_changes == 0` and the view is frozen or moves sub-pixel |
| C overlap / hole | `overlap_pairs > 0` or `drawn_is_partition` false on any frame |
| D skirt artefact | none of A-C fires, flicker only at piece borders; z-fighting is ruled out analytically if reverse-Z Depth32Float resolution (relative step about 6e-8 of distance) is far below the skirt depth `SKIRT_MARGIN * eps(L-1)` |
| E colour-class pop | the palette band (sand/green edge at height index 3 of 64) differs between a parent sample and a child sample for the same direction; measured as the fraction over seeded directions and levels 6..14 (a handover pop, fixed by plans 22-25, not here). Palette mip shimmer is ruled out by construction (`mip_level_count: 1`, mipmap Nearest) |
| F f32 jitter | worst f32 camera-relative error (about 6e-8 of the origin-to-camera distance plus 6e-8 of the cell bound radius) exceeds the skirt depth or 1/10 pixel at the drawing distance |

Several rows can hold at once. If no row matches: documented finding, no speculative fix.

### Verdict, row by row

- **C overlap / hole: ruled out.** `overlap_pairs == 0` on every frame of every run (hex and cube, scripted and fast, BEFORE and AFTER) and the drawn cut was a closed partition on every frame after the first complete cover (`partition=0` on 0 frames). The negative control (a hand-built parent plus child) gives `overlap_pairs == 1`, so the counter can fail.
- **A2 residency churn: ruled out for the fast descent, present but explained for the slow one.** Hex fast: `destroyed == 0` on all 380 frames. Hex slow: 93 frames with destroyed meshes (cube fast 36, cube slow 152), and the flip-flops near them are the explained ones (the counter attributes a flip-flop to a destroyed cell or its parent or child); no unexplained flip-flop had a destroyed or evicted cell within the 8 preceding frames (0 of 16, 47, 30 and 51 flip-flop frames in hex fast, hex slow, cube fast and cube slow).
- **A1 selection churn: HIT, and traced to its mechanism.** BEFORE, `flipflops_unexplained` was 24 (hex fast), 68 (hex slow), 103 (cube fast), 157 (cube slow) cells, on 16 to 51 frames, with `trimmed_splits`, `node_budget_hit`, `leaf_budget_hit` and the effective-cut coarsen stage all quiet. To find the cause every un-split (a cell in last frame's split set and not in this one) was classified (`topology::select::unsplit_reasons`): over every BEFORE run the count of cells dropped because `rho` fell below the hysteresis band was 0 and the count dropped within the band or above tau (budget, trim, loop stop) was 0; every un-split was either a cell culled by the selection (frustum or horizon) or a descendant of one (cascade). So the existing hysteresis (0.2, `hysteresis_band_has_zero_toggles`) is sufficient; the cause is that `select_cells` never evaluates a culled cell, so a cell that leaves the frustum or the horizon drops out of `prev_split`, loses its hysteresis and its split, and when it returns within a few frames it is split again (its children vanish and reappear). All 144 unexplained flip-flop frames (16 + 47 + 30 + 51) had a selection-culled un-split in the 8 frames before. The hysteresis is bypassed exactly through the cull path.
- **B cull toggling: present, not a defect.** `cull_toggles > 0` in 51 to 215 frames per run, all during camera motion (the draw cull of the piece set changes as the camera turns); with the camera frozen after convergence it is 0 (`frozen_camera_has_zero_churn_after_convergence`, hex and cube). The selection and the draw pass disagree on visibility only rarely: a cell that the selection dropped as culled but the draw pass drew visibly occurred on 6 of 380 frames (hex fast), one cell at a time (two for cube).
- **D skirt z-fighting: ruled out analytically.** Reverse-Z `Depth32Float` has a relative step of about 6e-8 of the distance. The shallowest skirt is level 16: `SKIRT_MARGIN * eps(15) = 1.5 * max(0.25 * 8.45 m, sagitta) = 3.2 m` (hex N = 16, sample spacing 277 km / 2^L), and a level-16 cell is drawn within a few hundred metres, a depth step of about 3e-5 m; the coarsest drawn cells are at the horizon (about 1100 km from 100 km altitude, step 0.07 m) with skirts of kilometres. The margin is at least four orders of magnitude everywhere.
- **E colour-class pop: ruled out as the main cause (proxy).** Over 4000 seeded directions per level, the fraction whose palette segment (sand/green/brown/grey/white) or mask row differs between a linear interpolation at the spacing of level L-1 and of level L is 0.0010 at level 6, 0.0003 at levels 7 and 9, and 0 at levels 8 and 10-14; the palette x index (1/64 of the height range) differs in at most 0.9% (level 6) and 0.03% from level 10 on (`colour_class_pop_fraction_by_level`, prints the table). The proxy interpolates the terrain function; it does not render, so a colour jump caused by the geometry change itself is not covered. Palette mip shimmer is impossible by construction (`mip_level_count: 1`, mipmap Nearest).
- **F f32 camera-relative jitter: ruled out.** Error about `6e-8 * (d + r)` (translation plus vertex offset, `d` camera to cell origin, `r` cell radius, about 12 sample spacings). It exceeds a tenth of a pixel (`1.6e-4 * d` with the 720 px, tan(half fov) 0.577 projection) only when `d < 7.5e-4 * r`, that is a cell origin within metres of the eye (a level-8 cell has r about 13 km, so d < 10 m); far below the skirt depth (3.2 m) it never matters.

Rows hit: **A1** (mechanism: culled cells drop out of the split set). Everything else is ruled out or benign. These are analytic estimates for D and F and a proxy for E, recorded as such.

### What was visible in the user's flight?

Honest scope of the evidence: BEFORE, most of the churn the fix removes is off screen (the cell is culled because it is outside the frustum). The on-screen consequence that was measured: 4 to 20 frames per run where a cell the selection dropped as culled was still drawn visibly (a coarse piece where the children had been), at most one or two cells per frame. That is a real but small visible flicker; whether it is the "green patches" the user saw cannot be decided headless. What is certainly continuous in the fast descent is plain refinement: `level_changes` p95 of 20 to 50 events per frame in the high bands and p95 13 (max 90) below 100 m. That is level-of-detail popping (geometry and the height-indexed colour change at every handover); it is not a flip-flop and this plan does not change it (plans 22-25: geomorphing, colour continuity).

### Fix (A1) and its cost

`topology::select::retain_culled` (called by `TerrainSystem::prepare` after `select_cells`; `select_cells` itself is unchanged, so the cube goldens hold): a cell that was split last frame and is culled this frame (frustum or horizon) stays split, shallowest first, only while all its parents are split, only within the piece budget the visible selection left over, and for at most `TerrainConfig::retain_frames` (default 8, 0 disables) consecutive frames. Pieces that exist only because of the retention are drawn when resident but never requested (a first version requested them and pushed the fast-descent lag to 11 > 10 in `streaming_lag`; fixed, bounds unchanged). Cost: prepare grows by about 1 ms (hex) and 0.5 ms (cube) at p95 in release (hex worst band p95 10.75 ms against the 16.7 ms budget; cube 2.06 ms).

Tests that failed before the fix (deterministic, debug, counted):

```
planetary-core lod_select culled_previously_split_cells_stay_split (with the retention call removed):
  36 previously split cells were dropped because they were culled: [PatchId(432345564227568630), ...]
planetary-app flicker monotone_descent_has_no_unexplained_flipflops (before the retention existed):
  Hex Scripted frame 22: 1 flip-flops, trimmed 0, node budget 0, leaf budget 0, coarsened 0, destroyed 0
planetary-app flicker without_retention_the_flipflop_counter_fires (retain_frames 0, keeps passing as the negative control):
  retention off: 802 unexplained flip-flops during the descent
```

AFTER: `flipflops_unexplained` is 0 on every frame of all four bench-stream runs, of the counted tests (hex and cube, scripted and fast) and of the real window run (48 before, 0 after). The flip-flops that remain are explained: a retained cell older than `retain_frames`, a cell rejected for the piece budget, a destroyed cell, a trimmed or coarsened frame. Each of these flags is a counted reason; a retention expiry means the cell was invisible for more than 8 frames.

Before the expiry flag was part of the explanation, the residual unexplained frames were hex slow 9, cube fast 11, cube slow 11 (hex fast 0), and every one of them had a retention expiry within the 8 preceding frames (9/9, 11/11, 11/11). That is the one place where an explanation was added to make an invariant hold, so it is stated here: expiry is a design bound (stale splits must not live forever), not evidence against the cause.
