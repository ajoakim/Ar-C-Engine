# Phase 07.1 Plan 19: Streaming throughput Summary

Detail now reaches the camera in roughly half to a third of the frames it did, and after arrival at the surface the scene converges in 48-59 frames instead of 133-169 (release, free-running workers). The hypothesis was CONFIRMED. The level lag at the camera DURING a very fast descent is only partly fixed (p95 stays 8-9 levels in the paced release run); that part is bounded by chain depth and the scripts' ground speed, not by the caps (see Known limits).

HYPOTHESIS CONFIRMED. Frames-to-detail was 198-224 (4.4-5x over budget); supply 70-83 patches/s against caps that allow 120/s; `awaiting_upload` 72-100 and queued 20-48 show generated patches waiting on the upload cap while workers were idle (33 ms paced and unpaced control identical); cancel churn, eviction and `max_pending` backpressure were all zero or far below limits, so those candidates were refuted. The settle control is no better than async: the existing tests hid this only by never asserting lag during the descent. The harness' raw "throughput ratio" (uploads over distinct leaves ever wanted, 0.04-0.06) overstates the gap because transient leaves count as demand; I report uploads/s and convergence instead.

## What changed and which number justified it

- **Adaptive caps** (upload 4/8/16 base, hard maxima 32 uploads, 64 starts, 128 requests; target 8 ms of prepare plus gpu_frame): justified by uploads/s 70-83 and awaiting_upload 72-100. Scale = damped target/cost in [0.25, max/base]; fast frames grow, slow shrink, absent/NaN/negative cost gives the base caps. Mechanism (stream manager and upload byte cap fixed at construction): in adaptive mode they are built at the hard maxima, throttled per frame by the number of requests issued (queue <= 2 frames of starts, in flight <= 3 frames of uploads) and an uploader wrapper that refuses uploads over the cap (they stay CPU-ready). Off by default; the app enables it (`AppSettings::adaptive_streaming`), the example turns it on for all wall-clock runs. Recorded in an ADR-0012 amendment.
- **Priority order**: roots first (a missing root is the only unavoidable hole; found when `descent_degrades_with_one_start_per_frame` showed a hole at frame 10 without it), then screen-space error over distance (`geometric_error * proj_scale / max(distance, 1 m)`, exact ops), ancestors inherit the best score; ties by (level, raw). `plan_requests` keeps its old behaviour as a wrapper. Ordering alone (an intermediate `--no-adaptive` run, taken before the closure-touch fix: fast frames-to-detail 182, uploads/s 82, lag p95 14) did not fix the lag; the caps did, so ordering is a secondary gain.
- **Short queue / in-flight window**: needed so the nearest-first order is not stuck behind a stale FIFO backlog (the manager orders by priority class then FIFO). Window 2 frames of starts rather than 1, because `stale_requests_are_cancelled` needs a small backlog to exercise cancellation.
- **Fallback chain kept resident**: the first adaptive run (about 3200 uploads, 1600 evictions) showed the camera falling back to level 3: ancestors of a drawn leaf are never drawn, so they were the oldest in the residency LRU and were evicted first. The wanted closure is now touched every frame (`manager.resolve`), reported as `closure_cells` / `closure_resident`. Partition holds every frame under eviction (test with `detail_budget_patches` 120 evicts 400+ and stays a partition).
- **Dropped**: the churn guard (no request cancellations were observed: `cancelled` 0 in every run).
- Hard maxima: first set at the plan's example 16/32/64, raised to 32/64/128 after the first measured run showed arrival convergence upload-bound (96-117 frames at 16 uploads/frame). The cost controller, not the constant, limits the frame time (release cost 1.5-4 ms; caps settle at 8-20 uploads when eviction raises the cost).

## Deviations from Plan

1. [Rule 1/3] Roots-first rule added to the planner (hole at frame 10 in the existing one-start-per-frame descent test otherwise). Existing tests not weakened.
2. [Rule 3] Fixed request caps reinterpreted as base values; adaptive mode is opt-in (`TerrainConfig::adaptive`, `AppSettings::adaptive_streaming`) so the existing descent and terrain tests keep their exact caps. `TerrainReport` gained `closure_cells` / `closure_resident`.
3. The plan's counted yield pump was replaced by `wait_for_workers` (a blocking settle on started jobs, test/bench only): the yield pump made debug results depend on machine speed (convergence 157-321 frames, varying per run). No sleep or clock is used.
4. `TerrainSystem::set_frame_cost` is fed by the app from telemetry (`prepare_ms + gpu_frame_ms`), as planned; under `SimClock` the cost is a constant, which the tests use at 0.2 ms (caps at their hard maxima). Slow-frame throttling is covered by `terrain_stream` unit and system tests.
5. Task 3 step 2 windowed `--descent --frames 1800` and a fast windowed run were executed (exit 0); the fast windowed run needed `--fast` to select the fast script with `--descent` (added).

## Known limits

- Level lag during the descent itself is not fixed: at the scripts' ground speed (tens of km/s at low altitude) every new patch needs a chain of ancestor round trips (one level per frame at best, ancestors-first), so p95 stays 8-9 levels in the paced release run (frames with lag > 1 fell from 60% to 25-32%). Predictive prefetch along the velocity would be the next lever; not done (outside this plan).
- About half of the uploads are transient patches evicted soon after (3143 uploads vs about 1600 held); each upload at the residency budget triggers an LRU eviction scan inside engine-streaming (O(n log n) over all records), which raises the frame cost to 3-4 ms and pulls the adaptive caps down to 8-9 uploads per frame near the surface. Fixing that needs a change in `crates/engine-streaming` or a larger `detail_budget_patches`; neither done here.
- Windowed pacing is present-bound at about 31 ms (07.1-05); the paced bench spins 33 ms per frame. The final visual check remains the user's flight.
