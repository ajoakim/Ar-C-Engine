# Limitations

Known limitations of the engine and its reference applications, consolidated from the ADRs and the phase evidence. Each item states the impact and where it would be resolved. "Plan NN" refers to a Phase 8 plan (`.planning/phases/08-hardening-decisions/`); items assigned to a plan that has not run yet are open at the time of writing. See [assumptions.md](assumptions.md) for the premises these limitations sit on.

## Verification gaps

- **Phase 07.1 closed complete-with-caveats.** The human window flight was approved by the user without numbers: no bench table, CSVs, `perf:` lines, title readouts, `gpu:` startup line, refresh rate or present-mode comparison were supplied. The caveats (07.1-18 summary) are: C1, the visual approval is not definitive without meshes ("I would need meshes to exist for then to be definitive"); C2, the plan 26 present-mode and window-title readout checks were not exercised by the human on this code (the run shown used an older checkout whose usage text lacks `--present-mode`); C3, no user-supplied numbers, so release bench and telemetry claims rest on agent-measured evidence (earlier plan summaries and ADR-0016); C4, Linux and macOS goldens were pending hosted CI. Resolution: plan 12 (final gate and human flight).
- **GPU image goldens exist only for Windows (WARP).** Linux (lavapipe) and macOS image goldens are still pending (plan 11): without them the Linux and macOS image-diff runs print a skip line and pass. The hosted `windows-latest` WARP result may also differ beyond the 2/255 and 0.5 percent tolerances, and the Linux and macOS tolerances are uncalibrated (ADR-0005 amendment). The CPU goldens (heights, hex directions, hex mesh, cube select) are not affected: they passed on all three operating systems in hosted run 45947523739.
- **macOS has no software image-diff adapter.** There is no software Metal adapter, so the macOS image job cannot require one; macOS image goldens, when added in plan 11, must come from whatever adapter the hosted runner offers (ADR-0005 amendment, `ci.yml`).
- **Hosted benches are not run.** The criterion benches (spatial, select, mesh, stream, ecs) were measured locally on one Windows machine with `--quick` sampling; no CI bench job has run and there are no timing gates (plan 11). Treat single-digit-percent differences as noise (ADR-0017 measurements).
- **The overlay has not been looked at in a window.** The F3 overlay is covered by headless tests and an offscreen image test (WARP), not by a windowed flight, and the surface-target path is exercised only through the code it shares with the offscreen one (plan 08-08 summary). Confirmation is plan 12. Linux and macOS overlay goldens do not exist (plan 11).
- **There is no hashed morph golden.** Geomorphing is covered by invariant tests only (`08-CI-EVIDENCE.md`).
- **The empirical hex properties are not proofs.** The 2:1 balance (maximum level jump 1) was measured on 40 random sets, 12 pentagon distance-rule sets and 30 real selection cuts, plus the seam proof; if a jump of 2 is ever seen the rule must be revisited, not the assertion weakened. The S4 skirt model is loose (validated to coarse level 4 on the real hierarchy and with an interior construction to level 19) and does not validate the 1.5 margin against the engine's real LOD error measure. The gnomonic Voronoi differs from the spherical one on 1.18 percent of 10,000 samples, so code must stay on the lattice definition (ADR-0011).

## Rendering and terrain

- **Distance haze, not an atmosphere.** The engine has a generic distance fog and the planetary app uses it for a haze and sky colour. The values are first guesses to be judged by eye and the human judgement is still pending (ADR-0015). There is no atmospheric scattering model. The minimal atmosphere (ADR-0019, plan 10) is an opaque limb ring mesh plus a sun-tinted sky colour: no scattering model or look-up table, no alpha blend (the pipeline is `REPLACE` only, so the ring cannot brighten the planet disc or blend over it), and the ring deviates from the "shader pass" CONTEXT asked for because a shader or blend mode would be a core change. Its constants (100 km height, spread 2, twilight tint) are first guesses and its look has not been judged by a human yet (plan 12 decides whether to accept it or defer PLAN-08).
- **f32 per-patch origin quantisation.** Terrain pieces store an f32 origin plus offsets; reconstruction error was measured at 0.31 of a bound that is below the skirt depth, but it is a precision floor at very fine levels (ADR-0010).
- **The shading normal is unmorphed.** Geomorphing moves vertex positions, but the shading normal is not morphed (ADR-0014), and a morphing hex cell uses an approximation of the parent's normal and colour (border stencil rather than the parent's interior stencil), not separately tested for hex (ADR-0015).
- **Cross-level normals differ slightly** at LOD borders (ADR-0010).
- **Morph payload cost.** Payload v4 costs about 62 percent more bytes per cell, so residency byte budgets are hit earlier at equal settings, and worker mesh time grows (ADR-0014). Generator v2 adds about 23 percent more noise octaves (ADR-0015).
- **Rock appears only at fine levels.** From orbit the planet is coloured by height band and mask (ADR-0015).
- **Hex streaming trails cube on convergence.** On the final 07.1-27 measurements hex frames-to-detail is within 25 percent of cube only on the adaptive runs, by two to three points, and convergence after arrival is 73 frames for hex against 50 for cube; non-adaptive runs remain generator-bound. Hex costs about nine times the cube per frame in selection and generation (ADR-0011, 07.1-27 summary). It stays inside the 16.7 ms headless budget, but whether it "streams detail quickly" enough is the user's call (plan 12).
- **Present-bound Fifo cadence on the tested machine.** On the measured machine (Intel Arc B580, Vulkan, 60 Hz monitor, supported modes Immediate and Fifo only) windowed frames under Fifo were about 31 ms while CPU work was about 11 ms, so roughly 20 ms per frame was spent waiting for the present. Mailbox is unsupported there, so the default stays Fifo; `--present-mode immediate` removes the wait but can tear (ADR-0016). Other machines have not been measured.
- **Headless benches measure CPU time only.** GPU time is not included (planetary-app README).

## Platform

- **Linux Wayland display handle.** On Linux Wayland the instance may need the display handle at creation. This was deferred to Phase 8 and is still open and unresolved (ADR-0005 amendment). It is recorded here and not planned in this phase.
- **Local verification has been Windows-first.** Linux and macOS run in hosted CI for the CPU tests; no windowed run on those platforms is recorded in the phase evidence.

## Architecture and scope

- **No ECS.** Scene code uses `engine_world::World` (ADR-0017). The spike measured transform storage and hierarchy only (not multi-component queries, system scheduling or parallel iteration), and `World` is slower than `hecs` in every measured case (for example 43 times on a bulk local-transform sweep at N = 1e5, though that is about 40 ns per entity). The revisit triggers are in ADR-0017.
- **Spatial index update cost.** The hash grid (ADR-0006) answers queries in roughly constant time, but moving 10 percent of the entities and back is 8 to 24 times slower than the linear scan at every measured N (7.66 ms against 906 us at N = 1e5). Below a few hundred queried entities the linear scan is as good or better. rstar and kd-tree backends were not benchmarked, and the oversize-list and non-uniform-density concerns have no benchmark (ADR-0006 amendment).
- **The overlay is read-only.** It shows a `DiagnosticsSnapshot` and has no controls that change engine state (ADR-0018). The `egui-overlay` and `debug-overlay` features are off by default.
- **One planet, one world.** There is no multi-body support, no persisted cache format (v3 payloads are rejected, ADR-0014) and no editor, scripting, physics or ray tracing (`CLAUDE.md`, ADR-0002).
- **APIs are not stable.** Backend and SDK surfaces grow per phase (ADR-0005), and wgpu breaks its API frequently.
- **A pinned parent still counts against the residency budget**, because `ResidencyManager` is pin-unaware and the streaming layer filters LRU candidates itself (ADR-0008).
